One part: NEW modules and tests; no UI/server edits yet, no git/full suite/build/exploration. Read only engine/scenario.js 1–55 (calendar helpers), consult/diary.js 35–50 (JSON parser), consult/report.js 99–117 and 139–160 (provider call shape), judge/providers.js 300–340 if needed for call arguments. Do not read giant files.

Create `web/src/life/plan.js` (browser-safe), `web/src/consult/life-plan.js` (provider call), `web/tests/life-plan-47b.test.js`. Use small cohesive functions, strict schema validation; no extra dependencies. UI integration follows next fresh run.

Exports / contracts for later integration:

1. `buildLifePlanInput({scenario, profile, messages, lang})` returns bounded plain data. scenario is engine scenario with household.members (id,label,role,work,workdays,schooldays,school and existing routine frequency fields). profile has field objects `{value,source,note}`. messages are chat messages with role/content; ONLY user text is evidence, max last 12 user messages / 12000 chars total. Preserve member ids and profile/known workplaces; no addresses beyond those already required in supplied scenario. Max 8 members. Facts/defaults clearly distinguished: base scenario routine values are ASSUMPTIONS unless matched to explicit profile-member fields. Existing scenario may have stereotyped senior/remote/pet defaults; never describe them as stated facts. Return stable input signature (stable JSON string or deterministic non-secret hash) for stale-plan detection; include selected homes/start_date/days so profile/home changes invalidate confirmation.

2. `validateLifePlan(raw,input)` returns normalized plan or throws concise error. Exact schema: `{members:[{id,changes:[{field,value,basis,evidence}]}], observations:[{code,member_ids,reason}], questions:[string], unmodeled:[string]}`. Every input member exactly once, no duplicate/unknown ids. changes whitelist: preferences (<=500 chars), workdays/schooldays (unique weekday codes, nonempty; explicit no-commute uses commute field), errands_per_week ({supermarket:0..7, convenience:0..7}), park_walks_per_week 0..7, clinic_visits_per_month 0..31, cafe_visits_per_week 0..5, vet_visits_per_month 0..4, home_office/dog_walk_morning boolean, commute `none` only (no invented destinations/routes/minutes/costs). basis is `stated` or `proposal`. `stated` requires nonempty exact substring evidence from the USER messages OR an exact explicit profile member value for that same field with a user-sourced profile (do not accept arbitrary profile JSON as a quote); quote preservation is traceability, not semantic proof: even stated extraction is reviewed by user before executing. proposal must visibly remain a proposal. Reject unsupported fields, out-of-range values, invented member IDs, arbitrary observation codes, invalid array sizes. Never silently drop unsafe fields. preferences evidence must be user text, never demographic inference. Max 15 changes/member, 8 observations, 8 questions, 8 unmodeled strings <=300 chars each. Observation codes allow commute, school, errands, walks, remote_days, clinic, pet_care, monthly_cost, daily_variation. member_ids must reference real input ids. All normalized plans retain input_signature, source:'muse', confirmed:false, days and model-supplied review items. Do not return/execute any model totals or destinations.

3. `confirmLifePlan(plan,input)` returns a copied confirmed plan only when signature matches and there are no unresolved questions (questions block starting). User can revise their text and generate a new plan to answer them. `applyLifePlan(scenario,plan,input)` requires confirmation and exact signature, deep clones scenario, applies ONLY whitelisted member fields. commute none => work {type:'none'}. Preserve homes, coordinates, work destinations otherwise, criteria, seed, days and engine values. Put short per-member observation context in `plan_context` (<=1200 chars) for daily decision prompts, plus scenario.life_plan as bounded confirmed metadata. Do not mutate originals. Preserve preferences already explicitly present if unchanged. Unsupported requirements stay visible as unmodeled, never treated as simulated. For legacy nearest school boolean, add unmodeled notice to the normalized plan that school routes are nearby POI proxies, not assigned/enrolled schools. Confirmed plans should not silently transform assumption into measured fact.

4. `lifePlanExplanation(plan, scenario, lang='en')`: generate truthful localized explanation using code calendar counts for this exact start date/days and each member's active work/school weekdays. Return structured `{headline, summary, members:[{id,label,work_days,school_days}], methods:[{code,text}], limitation}`. Explain one day hides weekday/weekend and repeated travel/routines; 30 days is a chosen comparison window, NOT mandatory/scientifically validated, not a forecast. For a non-30 day scenario don't hardcode 30. Do not invent improvements, fatigue results, noise/daylight/safety, school assignment, care/pickup coordination. Code-generated observation methods describe measurable events only; monthly_cost is separate financial assumption, never multiplied trip counts. No need to make every household use every observation. Full remote with commute none has 0 scheduled work travel days, not 0 hours worked. Cannot prove a home fits the user; identifies differences worth checking in person.

5. `summarizePlanRun(run,plan)` uses ACTUAL household trips only (agents household true or keys h1...), preserving record evidence; returns first_7_days and full_period counts + travel_minutes by member and purpose, actual observed day coverage, missing/unavailable counts. Count trips as trip legs, not visits; don't call two legs two visits. Never extrapolate a week, fabricate variance, or include background agents. This enables an honest "what a month adds" result later.

Provider module exports `LIFE_PLAN_PROMPT`, `writeLifePlan({call,provider,input,lang})`: one completeWithTools-compatible call with system+JSON user input, no tools, maxTokens 6000 (baseten 12000), timeout60s/180s. Response shape res.message.content; parse plain JSON / fenced JSON; validateLifePlan. Return {plan,usage} with call provenance provider/model if returned. Provider failure/invalid plan throws, never silently falls back to canned plan labelled Muse. Prompt must compose a plan from stated needs, not select a persona template. Exact JSON schema and bounds in prompt. Never add medical appointments for seniors, cafes for remote workers, vet appointments for pet owners, or same workplace for every adult without basis. Proposed optional routines are possible but clearly proposal and reviewable. Missing workplace/school/individual schedules are questions if necessary; child grade/age alone never establishes school assignment. Don't demand irrelevant information: remote-only people don't need workplace. Unknown unsupported constraints (night shifts, accompaniment, accessibility, childcare coordination, actual catchment assignment, noise/daylight) go to unmodeled or concrete question, not invented support. Respect stated workday and preference differences across household members. No diagnosis/private-health details. Household member mismatch should be a question, never silently omit a member. Rationale is generated by code from observations/calendar; model selects applicable observations with brief specific reasons only.

Tests must cover mixed households independently of role labels: single shift/unsupported, two adults different weekdays/preferences, four-person with differently aged children unknown actual schools, fully remote, senior still employed, pet owner without invented vet visits, multigenerational with stated errands. A single scenario combining roles must work without selecting one persona.
