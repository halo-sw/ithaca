## 0. Quick start

For judges and developers. Every path runs the same app as the public site.

| Path | You need | What you get |
|---|---|---|
| **No install** | A browser | The [live app](https://halo-sw.github.io/ithaca/?lang=en) with live Muse under a shared daily limit, or [a recorded month](https://halo-sw.github.io/ithaca/?replay=pangyo-reviewed-month&lang=en) that plays with no key |
| **[Docker](#run-with-docker)** | Docker | The public build on `localhost:8080` and its model relay on `localhost:8787` |
| **[From source](#run-from-source)** | Node 22 | The Vite dev server, with every feature the public site turns on |
| **[Rebuild&nbsp;the&nbsp;data](docs/development.md)** | Python 3.12, about 6 GB of raw data | The pipeline that builds each area from OpenStreetMap and building records |

**Keys are optional.** Without one, the header shows **Rule mode**: the engine still computes every number, and recorded months play in full. With your own `META_API_KEY`, the chat, plans, daily choices, report checks and voice run on Muse Spark 1.3 and Muse Voice, and the room-photo windows and diary picture call SAM 3.1 and Muse Image. Muse Spark Open runs only with your own Baseten key.

### Run with Docker

```bash
git clone https://github.com/halo-sw/ithaca.git && cd ithaca
cp .env.example .env      # optional: add your META_API_KEY
docker compose up --build
```

Open [http://localhost:8080](http://localhost:8080). The build downloads the runtime data the public site serves (about 130 MB, from the [`data-v1` release](https://github.com/halo-sw/ithaca/releases/tag/data-v1)). CI builds and starts these two containers without a key on every pull request. The relay reads area data from the public site unless you set `DATA_BASE_URL`. Like the public site, this build turns on the room-photo windows (SAM 3.1) and the diary picture (Muse Image).

### Run from source

```bash
git clone https://github.com/halo-sw/ithaca.git && cd ithaca
npm --prefix web ci
mkdir -p "$HOME/ithaca-data"
curl -L https://github.com/halo-sw/ithaca/releases/download/data-v1/runtime-data.tgz \
  | tar -xz -C "$HOME/ithaca-data"
set -a; . ./.env; set +a  # optional: load your keys (see .env.example)
ITHACA_DATA_DIR="$HOME/ithaca-data/data" VITE_SAM_PHOTO=1 VITE_MUSE_IMAGE=1 npm run dev
```

Open [http://localhost:5173](http://localhost:5173). The dev server answers the model routes itself, so no relay is needed, and the data stays outside the repo.

**Tests**

```bash
npm test                  # JavaScript, after the npm ci above
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/pytest -q       # Python pipeline
```

Tests that need locally built area data skip themselves on a fresh clone, as they do in CI.

## 1. Project introduction

**A home is the largest purchase most households make, yet it is often chosen in a hurry.** A few photos, a floor plan, a price and one short viewing decide years of daily life. In Korea, rising prices add the fear of missing out (FOMO), and the deposit-fraud (전세사기) wave has made a deposit lease, the usual alternative to buying, feel unsafe. How the home fits the household shows up only after moving in.

**Ithaca's agents live there first.** A household modelled on yours lives the same 30 days in each of two candidate homes: work and remote days, errands, parks, school routes, evenings at home, commutes and money. Muse Spark 1.3 plans each member's routine and makes their daily choices among real, mapped options. Code computes every route, minute and won, and the report is checked against the saved record before you see it.

You then compare whole months of life side by side, not only the commute, and decide what to check at the viewing before you buy or sign. The decision stays yours.

**Who it is for.** First-job workers, couples about to marry, young families choosing between two homes, and new hires moving to a city they have never lived in, like a Meta engineer looking along the Caltrain corridor.

## 2. Service summary

| You provide | Ithaca returns |
|---|---|
| Household members, workplaces, budget and preferences | Candidate homes on a map, with historical transaction references |
| Two selected homes and reviewed routines | The same household simulated over the same 30-day window in both homes |
| Your questions and priorities | A whole-life comparison: time (commutes, evenings at home), money (monthly cost of buying, 전세 or 월세, with taxes and loan assumptions), daily needs within a 10-minute walk, saved decisions with reasons, and a report linked to its evidence |

Next to the 30 days, each Korean home shows deposit-lease (전세) warning signals with an official-source checklist and labelled mock-loss scenarios, support programmes compared condition by condition, and official safety and school statistics with source and period. Homes are weighted only by your own priorities (**내 기준 점수**). Ithaca names no winner and never rules a deposit safe.

Current scenarios cover parts of Seoul and Gyeonggi, including Jamsil and Pangyo, and a separate Menlo Park / Meta HQ case. Plans can combine working adults, remote days, children, older members and pets. Missing or unsupported needs stay visible.

Historical transaction prices are reference data, not available listings. US rent inputs include ZIP-level estimates. Sources, assumptions and coverage limits are part of the comparison.

## 3. Problem definition

**People commit to a home for years without ever having lived in it.** For most households a home is the largest purchase they make. It is chosen from photos, a floor plan, a price and a short viewing, and how it fits each person's day shows up after moving in. A couple weighs two commutes, office and remote days, errands and time at home; a family adds school routes. A poor fit keeps costing time and money every month.

- **Korea: haste, FOMO and deposit fraud.** In June 2025 Seoul apartment prices rose 0.43 % in a single week, the largest weekly rise in 6 years and 9 months (Korea Real Estate Board, via [Newsis](https://www.newsis.com/view/NISX20250627_0003230658)). When prices climb, the pressure to buy before it is too late grows. Waiting in a deposit lease is no safe harbour either: since the victims' act took effect in June 2023, **41,559 cases have been officially recognised as deposit fraud (전세사기), and 75.9 % of the recognised tenants are under 40** (30s 50.7 %, 20s 25.2 %). 97.7 % had a deposit of 300,000,000 won or less (Ministry of Land figures, via [Herald, 2026-10-11](https://www.heraldk.com/article/2026101114382405541)). A day of traveling between neighborhoods may still end with pressure to decide.
- **US: you find out after moving in.** 45 % of US homeowners have at least one regret about buying their current home ([Bankrate, May 2025](https://www.bankrate.com/press-releases/nearly-half-of-homeowners-have-at-least-one-regret-about-the-purchase-of-their-current-home/)). Among people who bought in the past year, younger buyers more often regret the commute and the neighbourhood ([Realtor.com, Nov 2025](https://www.stocktitan.net/news/NWS/realtor-com-as-market-cools-buyer-regret-does-grzvemhi8uiu.html)). The US market has slowed (a median of 63 days on market in October 2025, in the same study), so there the problem is less haste than deciding without having lived there.

**What is missing is a way to live there first.** A route search shows one trip, and a listing shows the unit. Neither shows how a household's schedules, errands and costs add up over a month, or how two homes compare under the same conditions. Ithaca turns that into an explicit, reviewable comparison and a set of questions to take to the viewing.

**What it does not do.** A 30-day simulation cannot certify a lease or stop deposit fraud. Ithaca shows public warning signals, an official-source checklist and labelled mock-loss scenarios next to the commute, the money and the 30-day record. It never rules a deposit or a landlord safe, forecasts prices or tells you to buy. Public transaction, building and transit data are inputs; they do not prove that a simulated month matches real life.

**Why I built this.** I'm Halo, and I have been looking for a home to start married life in. The deposit-fraud news made a 전세 feel risky, rising prices made waiting feel risky too, and two people with very different routines made every option hard to judge. How well we would sleep, how crowded the commute would be, what the neighbourhood is really like: you meet these only after moving in. With that much money at stake, I wanted to live there first.

## 4. How the Muse agents work

**Muse proposes routines and makes bounded choices. Code computes the consequences. The report is checked against the saved run.**

How one conversation runs, top to bottom. Blue boxes are Muse, grey boxes are code, white boxes are you. Dotted arrows send work back.

```mermaid
flowchart TB

    direction LR
    U(["You: one sentence<br/>KO · EN · voice"]) --> A["Consult agent<br/>Muse Spark 1.3 or Spark Open"]
    A <--> T[("Tools<br/>profile · homes · real deals · transit")]
    A --> G["Guard<br/>numbers only from tools"]
    G -. "retry once" .-> A
  end
  subgraph S2["2 · Plan"]

  end

    direction LR
    P["Muse writes the report<br/>from the saved record"] --> C["Check<br/>code: numbers and IDs<br/>Muse judge: sentences"]
```

Code: [relay](relay/handler.js) · [consult agent](web/src/consult/agent.js) · [tools](web/src/consult/tools.js) · [guard](web/src/consult/guards.js) · [household plan](web/src/consult/life-plan.js) · [live household loop](web/src/judge/household.js) · [browser worker](web/src/sim-worker.js) · [report](web/src/consult/report.js) · [checks](web/src/verify/compare.js). Chart source: [docs/agent-workflow.mmd](docs/agent-workflow.mmd).

| Role | What happens | What makes it inspectable |
|---|---|---|
| Consultation | Muse uses tools to extract the household profile and search recorded housing data | Stated inputs and missing information stay distinct |
| Planning | Muse proposes each member's working days, remote days, errands and supported routines | The user reviews assumptions; **Adjust my routine** sends a correction back to Muse before confirmation |
| Daily decisions | At a choice point, Muse receives the person's preferences, routine, recent choices and map-backed options | It returns an allowed choice and reason; the record retains the options and model or fallback source |
| Simulation | The browser worker applies fixed schedules and computes routes, elapsed time and costs | Values come from the engine and its inputs; background residents use rules |
| Report and checks | Muse writes from the saved record; code checks supported numbers and evidence IDs; a separate Muse call checks eligible claims against cited events | Failed claims return for revision. Missing or failed semantic checks remain **unverified**; unsupported items are not counted as passes |

**One recorded decision:** in the published Pangyo run, the partner's options on a remote day were a park walk or staying home. Muse chose the park and saved the reason, “Matches evening park walk routine on remote workday.” The engine computed the 5.1-minute walk. This is an observed simulated choice, not evidence of what a real person would do. [Decision, options and run](docs/recording-v9.md#the-choice-shown-in-the-video).

### Where the models run

The **browser** hosts the UI, 3D playback and simulation worker. A **relay server** on Vercel (or local Docker) makes runtime model calls. Hosted service keys stay in the relay's environment. An optional user-supplied key is sent with that user's request.

| Model | Job | Runs on | Evidence |

## 5. Main service flow

1. **Describe the household.** Enter or speak the people, budget, destinations and preferences.
2. **Pick two homes.** Inspect candidates, transaction references and map coverage.
3. **Review and adjust the plan.** Read each member's proposed routine. Use **Adjust my routine** to change a condition, review Muse's revision, then confirm.
4. **Run the month.** Muse chooses among allowed options while code computes the consequences. A live run may take a few minutes; the UI shows progress and any fallback state.
5. **Inspect the comparison.** Open costs, commutes, source tags and the actual report-check timeline. Follow a saved decision's journey in 3D.
6. **Prepare for the real viewing.** Use the differences and unresolved questions to guide what you check. The user makes the housing decision.

**Why 30 days?** About four weekly cycles repeat working days, remote days, weekends and errands under the same reviewed conditions in both homes. The UI compares **First 7 days** with the **Full period**, including when extra days add little information. Thirty days is a chosen comparison window, not a validated minimum or a forecast. Monthly housing costs use separate financial assumptions.

## 6. Conclusion

Ithaca makes the everyday consequences of a housing choice visible and inspectable: a reviewed household plan, saved decisions, computed trade-offs and an evidence-linked report. The prototype demonstrates that workflow with real model calls and public-data inputs.

The useful outcome is a better-informed viewing and a clearer comparison. The final decision remains with the household.

## 7. Expected impact and next steps

The intended benefit is **less mental work when comparing homes, earlier discovery of routine mismatches, and clearer conversations about time and money**. These are goals to test, not measured customer outcomes.

| Next step | What to validate |
|---|---|
| Field study with 10–20 residents | Compare modeled journeys and costs with observed routines; record errors and whether the comparison changes the questions people ask |
| Broader route and data coverage | Improve missing destinations, workplace precision and transit assumptions; keep unresolved inputs visible |
| More household needs | Validate school-route data and coordination requirements before claiming support; retain explicit limits for enrollment, noise and daylight |
| Photo-based assistance | Evaluate window detection on real room photos before adding physical measurements or environmental claims |

Start with your household, inspect the assumptions, and use the result to ask better questions before you sign.
